# Journal — terminal-first workspace

Approved conversation scope, 1 October 2026: a working initial implementation from the larger docs, not the full roadmap. See ADR 002 for the reuse decision. Extended on 2 October 2026 (user-approved milestone) with a durable local runtime and up to four concurrent sessions; see [ARCHITECTURE.md](ARCHITECTURE.md).

## Outcome

Open an existing Git checkout, launch Claude Code or Codex in a real interactive terminal, stop and explicitly resume the exact native session. Manually propose project knowledge with evidence, approve/reject/withdraw it, retrieve only relevant approved/current knowledge for a task, and inspect the exact packet sent at launch. Transfer that knowledge between providers working sequentially in the same checkout.

## Contracts and bounds

- Desktop, local-only; no chat, SDK, agent loop, cloud, telemetry or model-based extraction (a deterministic, review-gated proposal inbox exists). Node >=24 for development. Up to four concurrent sessions owned by a separate local runtime process; native permissions/login remain authoritative. Sessions in the same checkout share its working tree; a session can instead run in a Journal-managed or imported Git worktree (intent before side effects, no force/stash/transfer, conservative removal). Research mode starts each CLI in its native read-only mode (an intent; changeable in-session).
- Project identity is canonical checkout root; record Git common-directory identity, branch and HEAD. Opening a project runs only bounded read-only Git queries; never executes repository scripts.
- Knowledge: candidate/active/rejected/archived; edits create immutable revisions and return to candidate. Categories: decision, constraint, convention, lesson, issue. Scope: checkout or exact branch; area: whole checkout or relative path. Repo-wide/cross-worktree promotion comes later.
- User-approved follow-up: category `brief` orients every Journal-launched session independently of task words. Checkout briefs describe repo purpose/structure; exact-branch briefs describe current progress and next steps. Current approved entries alternate checkout/branch, newest first, with at most four brief claims inside the shared 12-claim/6000-byte budget. Briefs require whole-checkout area, preserve admission/freshness/revisions, and disclose limits. See `PROJECT-ORIENTATION.md`. No automatic progress extraction or context in externally launched conversations.
- Status-update helper (user-approved follow-up): read-only, deterministic drafts of a repo overview or current-branch update from local Git commits, changed files and uncommitted paths. No model call or storage until the operator saves a candidate; approval is still required. Git-range evidence records base and HEAD and is stale when HEAD is no longer in the current history. See `PROJECT-ORIENTATION.md`.
- One-action Remember (decision D1, approved by the user on 4 October 2026; applied in Phase 9): a note may be admitted with one action, without a separate candidate step, only when its whole statement is on screen at that moment, and for Still true also the change to the lines it cites (the whole change from the note's base when the shown change was cut). The one-action paths are the wrap-up's **Remember** and **Remember all** (1-5 suggestions painted on screen, all or nothing), **Remember both** on Getting to know your project, and **Still true** in the out-of-date catch. Each writes a new immutable revision with its evidence checked in the same transaction and is audited with a distinct `via` set by the main process (`wrap-up`, `first-run`, `reaffirm`); the window cannot choose it. Still true sends the file hash it showed and is refused if the file changed since. Edits keep the two-step flow (candidate, then Remember in Memory). Nothing is admitted without a visible user action.
- Evidence: explicit user statement, a Git commit range for status updates, or a bounded tracked-file excerpt plus SHA-256 of the file. Only regular tracked files under the canonical root, no symlink escapes, sensitive filenames, binary files or files over 1 MiB. Any changed file invalidates eligibility conservatively. Source views revalidate paths. Manual review is needed to admit all candidates (one visible action, as above).
- FTS5 queries are escaped as data. SQL filters project/admission/branch before ranking; pages validate evidence and area. Max 100 eligible candidates after inspecting at most 1000 lexical matches, with a scan-limit warning. Max 12 whole claims, 6000 UTF-8 bytes per knowledge packet (2000-token estimate, not a measured ceiling), and 100 excluded records disclosed. Never trim qualifiers. SQLite/Git/evidence run in a worker; hashes are cached only within one operation, never across previews. While the user types, the composer preview (`previewSelection`) reads SQLite only: no Git, no evidence reads and no writes, so its notes are shown as not yet checked. After about one second of idle, the composer runs a full validating preview that stores nothing, and a launch validates again. Visible lists cap memories at 500, sessions at 100 and receipts at 50.
- Receipts preserve immutable snapshots of statements/sources/scope/revisions, checkout and knowledge packet. The first delivery update also records the exact literal launch prompt, including any task or resume notice; later uncertainty cannot change it. Prepared, submitted, failed, uncertain delivery; no acknowledgment claim. Empty knowledge is allowed. Initial tasks are separate from the knowledge byte budget.
- Metadata and reviewed content persist in SQLite WAL. No credential-file reads, raw PTY logs or keystroke storage. Obvious credential strings are rejected at knowledge entry; finite patterns are not a universal privacy guarantee.
- PTY output uses 256 KiB in-memory history per session, 8 KiB chunks and 64 KiB display credit per attached session; only the visible session streams. Reload, window close with keep-running and app crashes reconnect to the runtime, suppress replies to historical device queries and disclose history gaps. A runtime crash ends terminals: sessions recover as interrupted (or orphaned when a verified process survives), delivery becomes uncertain, and input is never replayed. Quitting asks whether to stop sessions gracefully or keep them running.
- Process ownership: signals use the live PTY handle until exit; after a runtime restart only a process whose PID, start time and command hash all match may be signalled. Stop is SIGTERM to the PTY group, then SIGKILL after 3 s. Surviving descendants are reported and ended only on explicit request.
- Observability: Claude hooks (per launch) report status, permission waits, Bash commands with exit codes and edited paths; Codex hooks (per launch, trusted once in Codex) report turns, permission waits and interruptions, and Cursor's per-launch plugin reports activity, with turn end only after the user opts in to Cursor turn status (see PROVIDERS.md); anything else is unknown. Commands are redacted and timelines are bounded metadata. Empty-task resume reuses the latest delivered retrieval query for the same project/provider/native UUID, supplies refreshed knowledge and never repeats the original task. The current packet replaces earlier Journal claims; exclusions use the same memory ID and revision shown at delivery. Failed launches and other native conversations cannot supply this history. A mismatched Claude hook UUID suspends automatic resume pending manual confirmation. Manual confirmation drafts belong to their selected launch only.
- Electron contextIsolation + sandbox; narrow validated IPC, sender-frame checks, CSP, no remote renderer content/navigation, terminal clipboard/link escape actions disabled. Only selected project IDs and owned session IDs can address operations. The runtime accepts only token-authenticated local clients.
- Keyboard focus, labeled controls, instant terminal/session actions (switching with ⌘1–4 on macOS, Alt+1–4 elsewhere; app shortcuts work while the terminal has focus), pointer-gated hover; no motion library or decorative transitions, nothing animates on a keyboard action, and reduced motion removes all motion (the one budgeted entrance is the once-per-install first-note moment). Live regions announce state changes, never terminal output. Light and dark themes meet WCAG contrast for text. A sidebar, the main column (New session or the session) and an inspector with Session, Files and Memory tabs.
- Retrieval: FTS5 porter stemming over statements and identifier/path aliases; area-scoped claims apply when the task names the path or a distinctive segment of it; duplicates (same numbers and polarity) are delivered once; possible conflicts are flagged at review and warned about at delivery. Still lexical; no embeddings.

## Acceptance

Task-only lexical matching normalizes case and removes a small set of English grammar words before the 24-term limit (`queryTerms`). It remains lexical OR, not semantic relevance. Project/branch briefs are intentionally independent of task vocabulary.

Fixture-only CI for macOS, Linux and (experimentally) Windows is prepared (staged until it can be activated); authenticated provider trials stay manual and local. No nightly or scheduled verification. Native Windows verification still requires a local Windows machine (see [WINDOWS.md](WINDOWS.md)).

Real SQLite restart/retrieval/receipt tests, traversal/symlink/credential/branch/stale exclusion tests, exact argv tests with shell metacharacters and spaces, owned PTY/resize/interrupt/reload tests, desktop flow adding and approving file-backed knowledge and starting a safe fixture terminal with the exact context. Native CLI startup smoke must report trust/auth failures honestly. Paid inference is not needed for deterministic acceptance; authenticated provider handoff is separately reported if unavailable.
